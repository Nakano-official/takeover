# シフト登録の自動化（時間割PDFの読み取り）— 構想のみ

**コードはまだ無い。** ここにあるのは「やりたいこと」と「始める前に確かめること」だけ。
いま着手しない理由と、めどが立ったと判断できる条件を残しておくためのメモ。

（`future/feature-b/` と違い、こちらは**一度も書いていない**。退避ではない）

---

## やりたいこと

`courses`（授業・担当・利用学生）の登録を、時間割の資料から自動で起こす。

いまは**職員が履修登録PDFを見ながら手入力**している（科目・教員・教室）。
クォーターごとに全件入れ直すので、ここが一番重い。

---

## 見送っている理由（2026-09-28 時点）

Python の OCR ライブラリを使う構成は、このシステムの前提に合わない。

- 外部データベース・外部サーバーを持たない（GAS Web App で完結）
- データは大学 Google Workspace 内に完結させる。個人情報を外へ出さない
- 職員が自走できること。開発者がいなくなっても動くこと

Python を動かす場所が無く、置いたとしても職員が保守できない。

## ただし「OCR そのもの」は GAS だけでできる

**この前提だけは誤解しないこと。** Google Drive は PDF・画像を Google ドキュメントへ
変換するときに OCR をかける。GAS からは**高度なサービスの Drive API** で呼べる。

- Python も外部 API も要らない
- ファイルは Drive の中から出ない（Workspace 内に完結する）
- 日本語も対象（変換時に言語を指定する）

つまり**「OCR ができないから無理」ではない**。止まっているのは次の3点。

### 1. そもそも OCR が要るのか

履修登録PDFに**テキスト層があるなら OCR は不要**で、ドキュメントへ変換するだけで
文字が取れる。スキャンした紙なら OCR が要る。
**まず実物1枚でどちらか確かめる。** ここで話がまるごと変わる。

### 2. 本当の難所は文字ではなく表の形

OCR も変換も、返ってくるのは**行の羅列**で、罫線や列の位置は失われる。
「この科目は何曜日の何限か」「担当は誰か」の対応づけは自前で組み立てることになる。
時間割は**表**なので、ここが読み取り精度をほぼ決める。

### 3. 間違いが静かに通る

登録結果が間違っていても、画面は普通に動いてしまう。
**違うコマに違う人が割り当たり、欠員通知が別の人に飛ぶ**。
自動登録をそのまま本登録にしてはいけない。
**「読み取り → 職員が確認・修正 → 登録」の確認画面を必ず挟む**。
シフト入力のカード（D44）に読み取り結果を流し込む形が一番近い。

---

## それより先に確かめること

**教務システムから CSV や表計算の形で履修データが出せるなら、OCR より確実で速い。**
資料が PDF なのは「人が読むため」であって、元データはどこかに構造化されて存在する。
自動化を考え始めたら、**最初に職員か教務課に聞くのはこれ**。

---

## 始める条件（めど）

- [ ] 実物の履修登録PDFで、テキスト層の有無と表の作りを確認した
- [ ] 教務システムから構造化データが出せないことを確認した（出せるならそちらへ）
- [ ] 読み取り結果を職員が直せる確認画面の形が決まっている（全自動にしない）
- [ ] 1ファイルぶんの処理が GAS の6分制限に収まる目処がある
      （収まらないなら、ファイルを分けるか時間トリガーで分割）

## 触ってはいけない前提

- **実物の履修登録PDFはリポジトリに入れない。** 利用学生の氏名が載っている。
  このリポジトリは Public（`.gitignore` で PDF は除外済み）
- 検証は架空のデータで作った資料で行う
