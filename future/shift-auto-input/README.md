## やりたいこと

受講登録確認表（履修登録PDF）から、手入力している内容を自動で起こす。
**読む資料は同じなので、出口が2つある。**

### (a) スタッフ自身の空きコマ　← こちらが本命

スタッフが自分の受講登録確認表を上げると、`available_slots` / `assist_slots` が埋まる。
いまはマイページで曜日×時限のチェックを手で全部付けている（テイクと介助で2面ぶん）。
履修が変わるたび、年2回やり直す。

**自分のデータなので安全**：間違っていても本人がその場で気づいて直せる。
「空きコマ＝授業が入っていないコマ」なので、読み取った格子の裏返しでよい。

### (b) 利用学生の授業（`courses`）

職員が利用学生の受講登録確認表を見て、科目・教員・教室を手入力している。
クォーターごとに全件入れ直すので重い。

ただし**他人のデータ**で、間違えると違うコマに違う人が割り当たる。
(a) で読み取りが固まってから手を付ける順が安全。

## 見送っている理由（2026-09-28 時点）

Python の OCR ライブラリを使う構成は、このシステムの前提に合わない。

- 外部データベース・外部サーバーを持たない（GAS Web App で完結）
- データは大学 Google Workspace 内に完結させる。個人情報を外へ出さない
- 職員が自走できること。開発者がいなくなっても動くこと

Python を動かす場所が無く、置いたとしても職員が保守できない。

## ただし「OCR そのもの」は GAS だけでできる

**この前提だけは誤解しないこと。** Google Drive は PDF・画像を Google ドキュメントへ
変換するときに OCR をかける。GAS からは**高度なサービスの Drive API** で呼べる。

- Python も外部 API も要らない
- ファイルは Drive の中から出ない（Workspace 内に完結する）
- 日本語も対象（変換時に言語を指定する）

つまり**「OCR ができないから無理」ではない**。

## 実物を見て分かったこと（2026-09-28・受講登録確認表1枚）

### OCR は要らない

PDF にテキスト層がある（埋め込みフォント・`/Type0`・`/ToUnicode` あり、スキャン画像なし）。
教務システムが出力した電子PDFなので、**文字はそのまま取り出せる**。OCR は不要。
→ 「OCR ができない」という論点は最初から無かった。

### 1枚に時間割が2つ入っている

先端理工はクォーター制なので、**3Q の格子と 4Q の格子が縦に並ぶ**（後期の1ファイル）。
セメスター制の学部は1つだろうが未確認。半期ぶんを一度に登録する運用（春に前期・1Q・2Q、
秋に後期・3Q・4Q）とは相性が良い。

### 格子の作り

- 横＝曜日（月〜日）、縦＝1〜7限
- 1コマ＝**3行**：`開講期・登録コード・単位・[確定]` ／ `授業科目名` ／ `担当教員名`
- 科目ごとに開講期が書いてある（`後期` と `３Ｑ` が混在する）。
  **格子の見出しではなくセルの表記を信じる**ほうが確実
- **6限・7限の枠は用紙にあるが中身は空**。開講されない（2026-09-28 に periods から外した判断と一致）

### 楽な道は無かった

用紙の下に `曜日 / 講時 / 開講期 / 登録コード / 授業名 / 単位 / 担当教員名` という
**一覧表のヘッダがあるが、中身は空**（集中講義など格子に載らない科目のための欄）。
通常の科目は格子にしか無いので、**格子を読むしかない**。

### 文字の横位置だけでは切れない

曜日の見出しは安定した位置にあるが（月18 / 火43 / 水68 / 木92 / 金117 / 土164 / 日203 文字目）、
セルの中身はその位置に揃っていない。特に**限の番号と同じ行に科目名が寄る**。
横位置は手がかりにはなるが、それだけで曜日を決めると崩れる。
`開講期・登録コード・単位` の行を先に拾い、続く2行と組にするほうが素直。

## 実現できるかを決めるのは、ここ1点

上の構造は **`pdftotext -layout`（手元の道具）で読んだ結果**であって、
**GAS が触れるのは Drive が変換した Google ドキュメントだけ**。
変換は文字を流し込み直すので、**格子がどう崩れるかが分からない**。ここが未確認。

### 2分で決着する実験

1. この受講登録確認表1枚を Drive に上げる
2. 右クリック →「アプリで開く」→「Google ドキュメント」
3. 出てきた文書を見る

- **表として出る／曜日ごとの並びが残っている** → 作れる。次はどう組み立てるかの話
- **全部が1列に流れて曜日が分からなくなる** → この道は行き止まり。
  別の入り口（教務システムのCSV、あるいは人が写す）を探すことになる

**着手するなら、コードを書く前にこれをやる。**
## それより先に確かめること

**教務システムから CSV や表計算の形で履修データが出せるなら、OCR より確実で速い。**
資料が PDF なのは「人が読むため」であって、元データはどこかに構造化されて存在する。
自動化を考え始めたら、**最初に職員か教務課に聞くのはこれ**。
