# 個別通知のスケール課題と簡略化の候補案

スタッフへの個別通知（現状：Google Chat Incoming Webhook）は、**1人1本ずつ Webhook を手作業で用意する**運用になっており、スタッフが増えると破綻する。その簡略化の候補をここに記録する。

> 関連：`CLAUDE.md`（通知方式の確定）、`docs/decisions.md` D3（連絡先DBは職員のみ）、`docs/backlog.md`（運用前提）。
> 作成：2026-06-16（検討中。まだ採用していない＝候補案）。

---

## 現状の整理（ボトルネック）

| 用途 | 保存先 | 手間 |
|---|---|---|
| 職員スペース向け | スクリプトプロパティ `CHAT_WEBHOOK_URL` | URL 1本のみ（1回で済む） |
| スタッフ個人向け | 連絡先DB `contacts.webhook_url`（1人1列） | **1人1本ずつ手入力 ← ここが限界** |

**問題の本質**：Incoming Webhook は「1スペースにつき手作業で1本作成」が前提。スタッフ数に比例して
「各自がWebhookを作る → 職員が貼る」が増殖する。実装は `src/Notify.gs`（`getStaffWebhook_` が `contacts.webhook_url` を読む）。

---

## 候補案

### A. Chatアプリ（Bot）化 ― 根本解決
- **仕組み**：Google Chat アプリ（Bot）を作り、`contacts.email` 宛に**個別DM**を送る。
- **個別Webhook**：**不要**（メールアドレスだけで届く）。
- **初期設定**：多め。Google Cloud でChatアプリ登録・ドメイン内許可（管理者/本部の承認が要ることが多い）。
- **評価**：スケールの根本解決。当初 CLAUDE.md が「Bot不要」を選んだのは手軽さ重視だったが、
  スケール問題が出た今は見直す価値あり。
- **前提確認**：Google Cloud でChatアプリを登録できる権限があるか。

### B. メール通知に切替 ― 最小コスト
- **仕組み**：`MailApp.sendEmail`（または `GmailApp`）で `contacts.email` に送る。
- **個別Webhook**：**不要**。
- **初期設定**：ほぼ無し（emailは既に連絡先DBにある）。
- **評価**：すぐ・確実に運用コストをゼロにできる。CLAUDE.md は「Gmailより確実に届く」でChatを選んだが、
  それは**Webhook運用コストとのトレードオフ**。ハイブリッド（職員スペース=Chat、個別=メール）も現実的。

### C. 自己登録フォーム ― 中間策
- **仕組み**：各スタッフが自分のWebhook URLを画面（Web App）から登録 → `contacts.webhook_url` に書き込む。
- **個別Webhook**：必要（本数は変わらない）。
- **初期設定**：小。
- **評価**：**職員の貼り作業は無くなる**が、Webhook作成の手間自体は各自に残る。根本解決ではない。

### D. 共有1スペース＋@メンション ― Webhook 1本
- **仕組み**：「代行募集」用の共有スペース1つに候補者を **@メンション**して投稿（Webhookは1本）。
- **個別Webhook**：**1本のみ**。
- **初期設定**：小。
- **評価**：全員に見える（プライバシー・通知ノイズの懸念）。@メンションには各自のユーザーIDが要る。

---

## 推奨（現時点）

- **二段構え**を推奨：
  1. **まず B（個別はメール）に切替**して運用コストをゼロにする（開発期限 9/17 に対して現実的）。
  2. 余裕があれば **A（Botアプリ化）** で個別DMに格上げ。
- C は「職員の貼り作業」だけ無くす中間策。D は通知が共有スペースに出る点で要注意。
