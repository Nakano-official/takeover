# バックログ（ブラッシュアップ・未対応項目）

Phase 1 MVP（機能A：欠員補充の自動化）は最低要件クリア・動作確認済み。
ここに、後で着手したい改善点・積み残しを記録する。

凡例：
- 🔴 **本番運用の前提**（磨き込みではなく、実運用までに必須）
- 🟡 **磨き込み**（後回し可。実証実験前にまとめて）
- ⚪ **要検討・定義不足**（仕様を決めてから着手）

最終更新：2026-06-14

## 1. シフト確認画面に「利用者が誰か」の情報がない　🔴

- 現状 `courses` シートは `day / period / staff_a_id / staff_b_id` のみで、
  **どの利用者（支援対象の学生）のテイクなのか**を持っていない。
- 誰のためのコマか分からないと、現場の確認・引き継ぎで支障が出る。
- **対応案**：`courses` に `user_name`（利用者名）等の列を追加し、
  シフト確認画面に表示する。データ設計の変更を伴う（要 architecture.md 反映）。

## 2. 全体シフトを職員が確認できない　🔴

- 職員はコマに登録されないため、自分視点だと「誰がどのシフトに入っているか」を把握しづらい。
- **対応案**：職員向けに「全コマ一覧（誰がどこに入っているか）」のビューを用意する。
  - 補足：`getDashboardData()` は全コマを返している。表示の組み方（フィルタ/並び）と
    時間割形式（項目3）と合わせて設計するとよい。

## 3. 時間割形式の表示にする　🟡

- 現状はテーブル（行＝コマ）。曜日×時限のグリッド（時間割）にすると一覧性が上がる。
- 項目2（全体シフト）と一体で設計するのが効率的。

## 4. シフト入力画面（input.html）の制作　🔴

- 現状コマは `courses` シートに手入力。職員が自走するには画面からの入力が必要。
- CLAUDE.md の「職員が自走できるUI最優先」に直結。`code.js` の `input` ルートは
  既に予約済み（今は「準備中」表示）。
- **対応案**：クォーター・曜日・時限・担当A/B（・利用者：項目1と連動）を入力 → `courses` に追記。

## 5. 「もともと1人テイク」のコマの扱い　⚪（定義不足）

- 人数が足りず最初から1人テイクのコマが存在する。
- 現状は「2人体制が前提 → 1人欠員＝必ず補充」だが、元から1人のコマでは
  欠員＝即「テイク不成立」など、補充ロジックの分岐が変わる。
- **要決定**：1人テイクコマをデータ上どう表現するか
  （例：`staff_b_id` 空 ＝ 1人テイク）、その場合の欠員時の挙動（補充必須か／職員対応か）。
- 仕様を決めてから `findCandidates_` / `submitAbsence` の分岐を実装する。

## 6. 「何日のテイクが空いているか」が分からない　🟡〜🔴

- 現状は欠員（vacancies）単位の管理で、日付軸で「この日の空き状況」を俯瞰できない。
- **対応案**：日付別ビュー（カレンダー的表示）で、その日のコマ・欠員・補充状況を一覧化。
  - Phase 2 の Calendar 連携と相性がよい。Phase 2 着手後に再評価。
