### 実データ投入前に対処（コード）

- 🔴 **9-1. personal_code 未登録者の予定が「登録漏れ」に化ける（偽陽性）**
  - `personal_code` が空の学生は実績側（CSV）で永久に突合できず、その人のカレンダー予定が
    全部「登録漏れ」として出てしまう。今は `unregistered` 警告に出すだけで一覧には偽陽性が混じる。
  - **対応**：`reconcileShifts_` に「突合可能な staff_id 集合（personal_code 登録済み）」を渡し、
    未登録スタッフの予定は「登録漏れ」ではなく **「照合不可（要確認）」** に分類する。
- 🟡 **9-2. CSVブロック解析が位置依存**
  - `ｱﾙﾊﾞｲﾄ先` 列の +1/+2 を開始/終了と決め打ちしている。実CSVの列順が違うと壊れる。
  - **対応**：各①②③ブロック内の `開始`/`終了` 列を**ヘッダー名で特定**して読む（`parseAttendanceCsv_`）。
- 🟡 **9-3. 時刻パースが `HH:mm` 限定**
  - 実出力が `HH:mm:ss` や全角コロンだと、その勤務枠が丸ごと無視される。
  - **対応**：秒・前後空白・全角コロンを許容する（`hhmmToMin_`）。
- 🟡 **9-4. 氏名突合が空白除去のみ**
  - 異体字（髙/高）・半角全角カナの揺れは拾えず突合漏れ（D7の弱点が残る）。
  - **対応**：NFC正規化・半角全角カナ統一を加える（`normName_`）。最終的には実カレンダーで一致確認（D7③）。

### 🔴 本番運用の前提（正確性）

- 🔴 **10-1. 職員側の確定処理が非アトミック（D1違反・二重確定）** — `Vacancy.gs` `confirmSubstitute` / `setVacancyResult`
  - 現状は「findRow で result 空を確認 → updateRow で上書き」の2段階で、間に候補者の
    `respondToVacancy`（`claimIfEmpty`）が割り込むと**先着確定を黙って上書き**する。
    候補Yに「決まりました」通知が出た直後に、シート上は職員が選んだXになる（両者出勤 or 無人）。
  - **手順**：
    1. `confirmSubstitute` / `setVacancyResult` の「事前チェック＋updateRow」を、
       `respondToVacancy` と同じ **`claimIfEmpty`（result が空のときだけ書く CAS）** に置き換える。
       `substitute_staff_id` 等の同時更新は claimIfEmpty の追加更新引数で渡す。
    2. 失敗（＝既に決着済み）時は「先着確定などで既に決着しています。再読み込みしてください」を throw し、
       manage.html 側で一覧を再取得する。
    3. `reopenVacancy`（result を空に戻す側）も同様に、`withLock_` 内で「期待した旧値のときだけ書く」
       compare-and-set にする（Sheets.gs に汎用 `updateIfEquals_` を足すか、claimIfEmpty を一般化）。
  - **確認**：GASエディタで2実行を模擬（confirm 直前に別実行で claim 済みにする）→ 上書きされず throw すること。

- 🔴 **10-2. ID採番が999で重複する** — `Sheets.gs` `nextId_`
  - `('000' + (max + 1)).slice(-3)` のため 1000 以降が `'000'` に折り返し、以後**全追加行が同一ID**
    （`C000`/`V000`）。courses は「過去分は削除しない」方針で1000行超えは現実的。
  - **手順**：`String(max + 1).padStart(3, '0')`（切り捨てないパディング）に変更。
    既存IDは可変長でも `parseInt(id.slice(prefix.length))` で読めるため移行不要。
  - **確認**：`nextId_` に max=999 相当のダミーで 'C1000' が返ること（一時テスト関数でログ確認）。

- 🔴 **10-3. 勤怠照合の恒常的な偽「登録漏れ」（9-1の拡張）** — `Attendance.gs`
  - (a) `personal_code` 未登録の学生：CSV行が破棄され、正しく登録していても全件「登録漏れ」（＝9-1）。
    (b) **職員**：カレンダーに職員名が入るシフト（職員対応）は勤怠CSVに出ないため毎月必ず赤表示。
    `unregistered` 警告は role='学生' 限定で (b) を拾えない。
  - **手順**：
    1. `runAttendanceCheck` で「突合可能な staff_id 集合」（role='学生' かつ personal_code 登録済み）を作る。
    2. `reconcileShifts_`（または予定側の組み立て時）で、突合不能な人の予定は
       「登録漏れ」ではなく **「照合対象外（要確認）」** に分類し、warnings 側に出す。
    3. check.html のサマリ・一覧に「照合対象外」の区分を追加。
  - **確認**：`testReconcile` に「personal_code 無し学生」「職員」のケースを追加して分類を検証。

- 🔴 **10-4. 再オープン後に代行依頼が誰にも再送されない** — `Vacancy.gs` `reopenVacancy`
  - 再オープンは notify_status を「未通知」に戻すだけ。`notifyNewVacancy` の呼び出し元は
    `submitAbsence` のみで、**再募集の通知経路が存在しない**（旧確定者への解除通知だけ飛ぶ）。
    全候補は「募集終了」を受信済みのため、放置すると無人で当日を迎える。
  - **手順**：`reopenVacancy` の末尾で `notifyNewVacancy(vacancyId)` を呼ぶ（候補の再抽出・
    notify_status 更新は既存実装がそのまま使える）。メッセージに「（再募集）」を付けると誤解がない。
  - **確認**：補充済→再オープンで、候補者スペースに再依頼が届き notify_status が通知済になること。

- 🔴 **10-5. 土曜コマの補充候補が構造的に0人になる** — `Forms.gs` `DAY_QUESTIONS` ×（Google フォーム本体）

  - **確認**：土曜コマで `findCandidates_` が空き申告者を返すこと（案A）／土曜コマが登録不可なこと（案B）。

## 11. 設計の理想形（アーキテクチャ方針の提案・2026-07-09）

### 11-1. 機能Bの「予定側」をカレンダー氏名パースではなくDB由来にする（最重要）⚪

- **現状**：照合の予定側は、カレンダー説明欄の**氏名の自由テキスト**を `parseEvent_` で取り出し、
  空白除去だけの正規化（`normName_`）で `staffs.name` と突き合わせている。
  氏名の表記ゆれ（D7）が構造的な弱点として残り続ける（9-4 の正規化強化は対症療法）。
- **観察**：このシステムは既に「誰が・どの曜日時限に・どのコマを担当するか」を
  courses × periods × vacancies（代行確定含む）として**構造化して持っている**。
  予定の正はDB側で組み立てられるはずで、カレンダーは本来「表示」であって「真実の源」ではない。
- **理想形（矢印の逆転）**：
  1. イレギュラー（休講・早終了・超過・担当変更）を**シートに記録**する（例：`irregulars` シート）。
  2. 予定（機能Bの突合対象）は **DB（courses×periods×vacancies×irregulars）から算出**する。
  3. カレンダーは **DBから自動生成**する（Phase 2 の「カレンダー自動反映」をこの向きで設計する）。
- **効果**：氏名が突合キーから消滅し、D7（表記ゆれ）問題そのものが不要になる。
  照合は staff_id 同士の完全一致になり、9-4・D7③（実カレンダー確認）の負担が大きく減る。
- **根拠**：`seedTestCalendar` のコメント自身が「イベントには staff_id / course_id を説明欄に入れて
  人物を特定できる形にしている（＝カレンダーにどう書けば機能Bが成立するかの設計案そのもの）」と
  述べており、方向性は既にコード内に示唆されている。
- **移行の現実解**：実カレンダーは手書き資産なので、当面は氏名パースを**フォールバック**として残し、
  「説明欄に staff_id があればID突合・なければ氏名突合」の二段構えで段階移行する。

### 11-2. 欠員（vacancy）のライフサイクルを「状態機械」として一箇所に定義する ⚪

- **現状**：「未解決 → 補充済／1人テイク／職員対応 → 再オープン」という状態遷移が、
  `respondToVacancy`・`confirmSubstitute`・`setVacancyResult`・`reopenVacancy`・自動決着に
  **ばらばらに**実装されており、遷移の前提条件が遷移ごとに抜けている。
  §10 の重大バグ 10-1（非アトミック確定）・10-4（再オープンで通知が飛ばない）・
  10-9（過去日に承諾できる）は、**すべてこの構造が根本原因**（同じ穴の別の出口）。
- **理想形**：状態遷移を行う関数を1つ（例：`transitionVacancy_(vacancyId, from, to, options)`）に
  集約し、そこで必ず（a）CAS（compare-and-set・ロック内での旧値検証）、（b）日付等の前提条件検査、
  （c）遷移に対応する通知、をセットで実行する。各公開関数はこれを呼ぶだけにする。
- **効果**：遷移の抜け漏れがクラスごと消える。将来「全員辞退で自動降格」（#5・requirements §8）や
  「休講」区分を足すときも、この一点に足すだけになる。

### 11-3. 「最新クォーター」を文字列ソートではなく学期マスタで解決する ⚪

- **現状**：`quarters.sort()` の末尾を「現在」とみなすロジックが3ファイルに複製されている
  （`code.js` getTimetable / `Input.gs` getInputData / `Vacancy.gs` getMyCourses）。
  CLAUDE.md 自身が「クォーター制は理工のみ・今後変更の可能性大」と明記しており、
  表記変更（例：`2026-前期` と `2026-Q3` の混在、`Q10`）で辞書順が壊れるのは確実に踏む地雷。
- **理想形**：`terms` シート（term_id・開始日・終了日）を1枚足し、
  「今日の日付が含まれる学期」を引く共有ヘルパー（`currentTerm_`）に3箇所を集約する。
- **効果**：セメスターとクォーターの混在に自然に対応。スタッフ空きコマの再収集サイクル
  （Phase 3・学部ごとに異なる）の基盤にもなる。

### 11-4. ステータス文字列の定数一元化 ⚪

- **現状**：`補充済`・`1人テイク`・`職員対応`・`承諾`・`辞退`・`欠員対応中` が
  サーバー5ファイル＋HTML3ファイルにリテラルで散在。
- **理想形**：サーバー側で定数オブジェクト（例：`VACANCY_RESULT` / `ANSWER`）を1つ定義し、
  テンプレート経由で画面にも渡す。表示ラベル・CSSクラスの対応もデータとして一緒に持つ。
- **効果**：「休講」のような4つ目の決着区分を足す日（イレギュラーパターンに休校がある以上、
  来る可能性が高い）に、7ファイル同時修正ではなく1箇所の追加で済む。

## 12. 運用上の未確認事項（コードだけでは判断できない・要ヒアリング）

2026-07-09 のレビューで挙がった、実運用に関わる確認事項。回答が出たら decisions.md / operations.md に反映する。

- ⚪ **12-1. 開発者不在後の「実行者」は誰か（最大の単一障害点）**
  - Web App は「デプロイした職員として実行」する設計。そのアカウントが GASプロジェクト・
    2つのスプレッドシート・カレンダーの実質的オーナーになる。
  - その職員の異動・退職時の**引き継ぎ手順（再デプロイ・オーナー移管・スクリプトプロパティの引き継ぎ）**を
    operations.md に明文化する。「職員が自走できる」を最優先に掲げる以上、ここが最重要。
- ⚪ **12-2. Webhook 未登録の学生には代行依頼が届かない（静かな未達）**
  - contacts.webhook_url が空の候補者は通知がスキップされるが、候補としてはカウントされる。
    「返事がない」の原因が職員から見えない。
  - **案**：manage 画面の候補一覧に「通知未達（webhook未登録）」の表示を追加する。
- ⚪ **12-3. 実カレンダーの記法は誰がどう守っているか**
  - 機能Bは「タイトル＝授業名（利用者名）教室、説明欄＝氏名改行区切り」を前提にするが、
    実カレンダーは職員の手書き資産。実イベントがこの形か（`inspectCalendarDay` での抽出成功率）が
    機能Bの成否をほぼ決める。実データ確認（9-6）の際に**最初に**見る。
    ※ 11-1 を採用すれば、この前提自体が段階的に不要になる。
- ⚪ **12-4. 空きコマの上書き更新と過去クォーターの関係**
  - available_slots はクォーター毎に上書き、courses は過去分を残す方針。
    過去クォーターの欠員を後から再オープンすると、候補抽出は「今の」空きコマで走る。
    実害は薄そうだが、意図した挙動か要確認。
