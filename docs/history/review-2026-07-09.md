## 🔴 正確性バグ（優先度順）

### 1. 職員側の確定処理が非アトミック（D1違反・二重確定の恐れ）

`Vacancy.gs` `confirmSubstitute`（374行目付近）・`setVacancyResult`（402行目付近）は
「`findRow` で `result` が空であることを確認 → `updateRow` で上書き」という**2段階の
check-then-act**になっている。この間に候補者の `respondToVacancy`（`claimIfEmpty` で
アトミックに書き込む）が割り込むと、**先着確定を職員の確定処理が黙って上書き**する。

具体的には、職員が manage.html で候補Xを「確定」しようとしている最中に候補Yが
respond.html で「承諾」をタップすると、Yの `claimIfEmpty` が先に成立して
「代行が決まりました」通知がYに送信される。直後に職員側の `updateRow` が
（古い読み取りに基づいて）`substitute_staff_id` をXに上書きし、シート上の確定者はXになる。
Yは確定通知を受け取っているのに実際はXが記録される。

→ 対策は `docs/spec/backlog.md` §10-1 に記載（`confirmSubstitute`/`setVacancyResult` を
`claimIfEmpty` ベースのCASに置き換え、`reopenVacancy` も同様に compare-and-set 化）。

### 2. ID採番が999で重複する

`Sheets.gs` `nextId_`（201行目）は `('000' + (max + 1)).slice(-3)` で3桁固定パディングしており、
既存の最大IDが999のとき次のIDは `slice(-3)` により `'000'` に折り返る。さらに
`parseInt('000')` は `0` のため、以後の `max` 計算も `999` から進まなくなり、
**それ以降に追加される全行が同一ID（例 `C000`/`V000`）** になる。

`courses` は「過去分は削除しない」方針（CLAUDE.md）でクォーターをまたいで蓄積されるため、
1000行超えは長期運用で現実的に到達する。`findRow`/`updateRow`/`claimIfEmpty` は
先頭一致した行を対象にするため、**新しいコマ・欠員の操作が無関係な古い行に誤って作用する**
恐れがある。

→ 対策は `docs/spec/backlog.md` §10-2 に記載（`padStart` 相当の切り捨てないパディングに変更）。

### 3. 機能Bの恒常的な偽「登録漏れ」

`Attendance.gs` の照合は2つの独立した穴を持つ：

- (a) `runAttendanceCheck`（85行目）で `personal_code` が空の学生の CSV 行は
  `if (!id) return;` で黙って破棄される。その学生が勤怠を正しく登録していても、
  彼らのカレンダー予定は**全件が「登録漏れ」として誤検知**される
  （`unregistered` 警告には出るが、差分一覧には偽陽性がそのまま混ざる）。
- (b) 予定側（`getPredictedShifts_`）は `staffs.name` に一致する全員（職員を含む）を拾う一方、
  実績側（勤怠CSV）は学生のみが対象。職員対応で入ったシフトはカレンダーに記録されても
  職員が労務管理システムに勤怠登録することはないため、**職員のシフトは毎月必ず
  「登録漏れ」として赤表示**される。

これは backlog #9-1 として既に把握されていた問題の再確認・範囲拡大（職員のケースを追加）。

→ 対策は `docs/spec/backlog.md` §10-3 に記載（「照合対象外（要確認）」という第4の分類を新設）。

### 4. 再オープン後に代行依頼が誰にも再送されない

`Vacancy.gs` `reopenVacancy`（433行目付近）は `notify_status` を「未通知」に戻すだけで、
候補者への**再募集通知を送る経路がどこにも存在しない**（`notifyNewVacancy` の呼び出し元は
`submitAbsence` のみ）。全候補は「募集終了」通知を受信済みのため、再オープンされたことに
誰も気づかない。放置すると、職員が個別に電話しない限り無人で当日を迎える。

→ 対策は `docs/spec/backlog.md` §10-4 に記載（`reopenVacancy` の末尾で `notifyNewVacancy` を呼ぶ）。

### 5. 土曜コマの補充候補が構造的に0人になる

`Forms.gs` の `DAY_QUESTIONS`（34行目）は月〜金のみを収集する一方、`Input.gs` の
`INPUT_DAYS` は土曜のコマ登録を許可している。土曜のコマに欠員が出ると、
誰も `available_slots` に「土n」を持つ手段がないため `findCandidates_` は常に0人を返し、
毎回「職員対応」に自動決着する。原因（フォームに土曜の設問が無い）が画面から分からない。

→ 対応方針は運用判断が必要（土曜運用の有無）。`docs/spec/backlog.md` §10-5 に案A/案Bを記載。

### 6. personal_code のテキスト書式が本番セットアップで1セルのみ

`Setup.js` `setupMainDb_`（299行目付近）の `'@'` 書式適用が `data.staffs.length` 行分しか
掛からず、本番用の `setupSpreadsheetsEmpty`（`staffs` が空配列）ではF2セルしか保護されない。
3行目以降に先頭ゼロの個人ｺｰﾄﾞ（例 `0123456`）を入力すると数値化され `123456` になり、
CSV側の文字列 `'0123456'` と永久に一致しなくなる（＝#3と同じ偽「登録漏れ」を招く）。

→ 対策は `docs/spec/backlog.md` §10-6 に記載（`migrateStaffsPersonalCode` と同じく `getMaxRows` まで適用）。

### 7. 未知の `?page=` で利用登録ゲートを素通りする

`code.js` `doGet`（42行目）の未知ページのフォールバックが
`renderPage_(PAGES[DEFAULT_PAGE], ..., getCurrentUser_(), {})` を直接呼んでおり、
既知ページに適用される「未登録ユーザー拒否」「`staffOnly` 判定」を迂回する。
未登録アカウントが `?page=` のタイプミス等でアクセスすると、
「利用登録がありません」ではなく空の `user={}` で home シェルが表示され、
その後の `google.script.run` 呼び出しが軒並みサーバー側で例外を投げる。

→ 対策は `docs/spec/backlog.md` §10-7 に記載（フォールバックを共通ガードに合流させる）。

### 8. `user.staff_id` が生セル値で厳密比較が破綻し得る

`code.js` `getCurrentUser_`（83行目）は `staff_id: contact.staff_id` を未加工で返す一方、
`Vacancy.gs` は `String().trim()` 済みのIDと `===`/`!==` で厳密比較している（42・93・128行目）。
`contacts` シートの `staff_id` セルが数値型や前後空白付きの場合、自己除外（候補0人の
自動決着ロジック）・重複欠勤登録チェック・相方氏名表示が軒並み不成立になる。

→ 対策は `docs/spec/backlog.md` §10-8 に記載（`getCurrentUser_` で1行正規化するだけで解決）。

### 9. 過去日の欠員に古いリンクから承諾できてしまう

`Vacancy.gs` `respondToVacancy`（220行目）には日付・期限の検査が一切なく、
作成時にのみ過去日を拒否する `submitAbsence` とは非対称。未決着のまま日付が過ぎた欠員に、
後日候補者が古いChat通知のリンクから「承諾」すると、遡って「補充済」が確定し、
関係者に確定通知まで送られてしまう。

→ 対策は `docs/spec/backlog.md` §10-9 に記載（`respondToVacancy` 冒頭に日付検査を追加）。

## 🟡 効率（優先度は正確性バグより下）

### 10. 「承諾」1タップで同一シートを15回超読み、通知を逐次送信

`respondToVacancy` → `isCandidate_` → `findCandidates_`（ctx未使用）→ `notifyVacancyFilled` の
呼び出し連鎖が COURSES/VACANCIES/STAFFS を都度全読みし、候補者ぶんの `CONTACTS` 読み取りと
`UrlFetchApp.fetch` も逐次実行される。`getVacanciesForManage` が既に持つ ctx 注入パターンが
この経路には適用されていない。複数候補が同時に承諾を競う瞬間に最も遅くなり、
ロックの `LOCK_TIMEOUT_MS`（15秒）に接近する。

→ 対策は `docs/spec/backlog.md` §10-10 に記載（ctx注入の横展開・`fetchAll` 化・列一括 `setValues` 化）。

## 確認した良い点（回帰させないため記録）

- **D1（先着確定の原子性）**：`respondToVacancy` は `claimIfEmpty`（LockService内 compare-and-set）
  で正しく実装されている。#1で指摘した非対称性は職員側パスのみの問題。
- **前回レビュー（2026-06-23）の指摘は全て解消を維持**：ダブルブッキング除外・欠勤日検証・
  クォーター絞り込み・手動決着時の通知・再オープン導線は今回のコード上でも健在を確認。
- **CLAUDE.md規約は全遵守**：認証情報の直書きなし（PropertiesService経由）、外部送信なし、
  実データ不使用（ダミーデータのみ）、`.clasp.json` 未コミット、シートスキーマ一致、
  15分丸めロジック（`round15_`）実装済み。
- **機能Bの設計方針そのものは妥当**：CSVをメモリ内のみで処理しシートに保存しない設計（D2/D14）、
  15分丸めでの比較（D14）は要件を正しく反映している。問題は突合対象の選定漏れ（#3）であり、
  照合エンジンのアルゴリズム自体は健全。
