## 総評

機能Aの**通常フロー（欠勤 → 候補抽出 → 先着自動確定 → 通知）は組み上がっている**。
競合対策（`Sheets.gs` の `claimIfEmpty` による compare-and-set）、ロール制御
（`requireStaff_` / `getCurrentUser_`）、メインDB/連絡先DBの2スプレッドシート分離など、
設計の骨格は丁寧に作られている。

一方で**不備は「候補スクリーニングの厳密さ」と「異常系の運用」に集中**している。
通常系は通るが、現実運用で起きるズレ・例外を吸収する作りになっていない。

実運用前に手当てすべき優先度：

1. #1 ダブルブッキング除外（補充の正しさの根幹）
2. #2 曜日チェック ＋ #3 クォーター絞り込み（低コスト・誤登録防止）
3. #5 通知の非同期化（GAS 6分制限）
4. #6 / #7 Webhook未整備・締切エスカレーション（運用で必ず効く）
5. #4 1人テイクの定義確定（backlog #5を決めてから分岐実装）

## 🔴 補充ロジックの正しさに関わる穴（最優先）

### 1. 候補抽出が「同時刻の別コマ担当・既に確定した代行」を除外していない＝ダブルブッキングの恐れ

`findCandidates_`（`Vacancy.gs:306`）は **`available_slots` の一致** と
**そのコマの staff_a / staff_b の除外** しか見ていない。チェックしていないもの：

- 同じ `day+period` で**別のコマ（別利用者）の担当**になっている学生
  （D8 で同一曜日・時限に複数利用者が並ぶ前提）。
- 同じ日時で**すでに別の欠員の代行に確定済み**の学生
  （`vacancies.substitute_staff_id` との突き合わせがない）。

`available_slots` はクォーター毎にフォームで別収集、`courses` は職員が別途入力するため、
**両者は必ずドリフトする**。さらに D1 の「先着自動確定」では職員が介在しないため、
**二重に入っている候補がそのまま承諾 → 確定**してしまう。要件 A-2（自動スクリーニング）の
品質を直接損ねる。

対策：候補抽出時に「その日付・その時限に、当人が他コマ担当か／既に代行確定していないか」を
`courses` ＋ 未解決・確定済 `vacancies` で除外する。

### 2. 欠勤日の曜日チェックがない

`submitAbsence`（`Vacancy.gs:50`）は `date` 文字列を受けるだけで、
**その日付の曜日が `course.day` と一致するか**を検証していない。過去日・対象外曜日でも
欠員が立ち、候補へ通知が飛ぶ。`date` が今日以降か／当該クォーター内かのチェックもない。
低コストで塞げる。

### 3. `getMyCourses` が全クォーターのコマを返す

`getMyCourses`（`Vacancy.gs:19`）は `isAssigned_` だけでフィルタし、**クォーターで絞っていない**。
「過去分は削除しない」方針（CLAUDE.md / requirements）のため、欠勤連絡の選択肢に
**過去学期の古いコマが累積表示**され、それに対して欠勤登録できてしまう。
現在クォーターに限定すべき。

### 4. 「もともと1人テイク」のコマで補充ロジックが破綻（backlog #5・未定義のまま稼働）

人手不足で最初から1名のテイク、および介助（常に1名）でも、欠勤すると
「2人体制前提＝必ず補充」で候補スクリーニングが走る。介助は skills で絞れるが、
**「1名のコマが欠員＝テイク不成立」の分岐がない**ため、補充できないケースの扱いが宙に浮く。
backlog で「要決定」のまま実コードに分岐が無いのが現状の不備。

## 🟠 運用で詰まりそうな箇所

### 5. 欠員登録が通知の完了を待つ同期処理（GAS 6分制限・UX）

`submitAbsence` が `notifyNewVacancy` を**同期呼び出し**し、職員スペース＋
**候補者人数分の HTTP POST** をその場で実行（`Notify.gs:69`）。候補が多いと欠勤連絡ボタンが
長時間ブロックし、CLAUDE.md が警告する**6分/回の制限**に近づく恐れ。
`docs/spec/notify-scaling-options.md` で検討済みのようだが、現実装は素の同期のまま。
→ 時間トリガー / キュー化を推奨。

### 6. Webhook未登録の候補には事実上届かない（フォールバックなし）

`getStaffWebhook_` が空なら `reason='Webhook未登録'` でスキップ（`Notify.gs:106`）。
実運用で個人 Webhook が揃わないと**候補は欠員を知らされず、誰も承諾しないまま放置**される。
全候補が未登録だと `notify_status` が `通知失敗` になるだけで、代替連絡経路がない。
運用チェックリスト（連絡先DB整備）と紐付けて潰す必要がある。

### 7. 締切・全員辞退時のエスカレーションが未実装（requirements §8 未決のまま）

回答が来ない／全員辞退のときの**リマインド・職員エスカレーションが無い**。
先着確定はあるが「誰も来ない」場合に放置される。要件 §8 で「未決」と明記された運用が
コードに無いのが現状の穴。

### 8. 職員の手動決着（職員対応 / 1人テイク）時に候補へ通知が飛ばない

先着自動確定（`respondToVacancy`）は「募集終了」を他候補へ送るが、
`setVacancyResult` / `confirmSubstitute`（`Vacancy.gs:263, 282`）は**通知ゼロ**。
職員が「職員対応」で締めても候補は知らされず、リンクを開いて初めて「確定済み」と分かる。
挙動が非対称。

## 🟡 軽微・設計上の留意点

- **候補集合が欠員作成時に固定されない**：`getVacancyForRespond` / `respondToVacancy` は
  毎回 `findCandidates_` を再計算（`Vacancy.gs:138, 167`）。通知後に `available_slots` が
  変われば、**通知された人が「候補ではない」と弾かれたり**、通知されていない人が回答できたりする。
  候補を vacancy 作成時にスナップショットすると安定する。
- **欠勤者名が全登録ユーザーに見える**：`getVacancyForRespond` は候補でない学生にも
  `absentName` を返す（`Vacancy.gs:136`）。「誰がいつ休む」が学生全員に見える。
  組織的には許容範囲でも一応の情報露出。
- **コマの状況表示が course 単位・最新 vacancy のみ**：`getDashboardData` / `getTimetable` は
  最新欠員の result だけ採用（`code.js:195`, `code.js:279`）。日付軸ではない（backlog #6 既知）ため、
  同コマで複数欠員があると過去の結果が埋もれる。
- **要件 A-6（代行記録のカレンダー反映）未実装**：`Calendar.gs` は読み取り診断のみ。Phase 2 として既知。

## 再レビュー（2026-06-23・修正4コミット反映後）

修正コミット `1744c59`（#1/#2/#3）/ `2d70204`（#8）/ `f44495e`（#4・D10）と、

### 合格（塞がれていることを確認）

- **#1 ダブルブッキング除外**：`findCandidates_` に `date` 引数を追加し、「同一クォーター・
  同スロットの別コマ担当」と「当日・同スロットで代行確定済みの学生」を `busy` で除外。
  `notifyNewVacancy` / `notifyVacancyFilled` / `isCandidate_` すべて `vacancy.date` を渡すよう統一。
- **#2 欠勤日検証**：形式・過去日（`dateStr < today`）・曜日一致（`weekdayOf_` vs `course.day`）を
  `submitAbsence` に追加。
- **#3 クォーター絞り込み**：`getMyCourses` が最新クォーターのコマのみ返す。`getTimetable` と一貫。
- **#8 手動決着の通知**：`setVacancyResult`→`notifyVacancyClosed`、
  `confirmSubstitute`→`notifyVacancyFilled` で先着確定と挙動を対称化。

### #4 の修正が持ち込んだ新しい不整合（要対応）

#### A. 自動決着した欠員は職員が管理画面から変更できない（案内文と実装の矛盾）🔴

`notifyAutoResolved` の本文は「変更が必要なら管理画面で対応してください」と案内するが：

- `manage.html:89` … `resolved`（result 入り）の欠員は「確定」バッジを出すだけで
  **操作ボタンが一切描画されない**。
- サーバー側も `confirmSubstitute`（`Vacancy.gs:328` 付近）と `setVacancyResult`（同 `:355` 付近）は
  両方とも `if (vacancy.result) throw '既に確定済み'` で**確定済みを弾く**。

候補0人で自動的に「1人テイク／職員対応」になった欠員は、後から職員が見つけた代行者を充てることも、
結果を変えることも**UIからは不可能**（シート直接編集しかない）。案内文が約束する導線が存在しない。
→ 対策：確定済み欠員に「再オープン」または「結果上書き」の導線を追加し、
自動決着＝暫定（D10の含意）と整合させる。

#### B. 「両方のスタッフが欠勤」のとき自動決着の結果が誤る（エッジ）🟠

`submitAbsence` の `remaining` は `course.staff_a/b` から**今回の欠勤者だけ**を引いて判定する。
2名テイクで相方が**別途すでに欠勤登録済み**でも `remaining=[相方]` となり「1人テイク」と判定されるが、
実際は相方も不在＝「職員対応」が正。`remaining` から「同コマ・同日に欠員が立つ他スタッフ」も
差し引く必要がある。

#### C. 即時自動決着の早すぎ問題（設計上の留意）🟡

候補0人の判定は**欠勤登録の瞬間の `available_slots`** に依存する。空きコマ申告が未整備だと、
本来補充できる場面でも即「職員対応」で閉じる。A の再オープン導線があれば緩和されるが、
現状は A が無いため影響が大きい。A とセットで考える。

## 確認した良い点（回帰させないため記録）

- 先着確定の競合は `claimIfEmpty`（LockService 内 compare-and-set）で原子的に処理されている（D1 準拠）。
- 全シートアクセスが `Sheets.gs` 経由に集約され、ヘッダー名で読むため列順非依存。
- Web App は「職員として実行」＋ `requireStaff_` のロール判定で、学生にスプレッドシート権限を渡さない設計（D4）。
- 端末エンドポイント（`Device.gs`）は件数＋最新連番のみ返し個人情報を出さない（D3 / D6 整合）。
- `google.script.run` の Date null 化対策（`dateToStr_`）など、既知の GAS 落とし穴に対処済み。
